⬅️ 목업 구현 페이지 보러가기

자동검사와 인간 검증의 결합: 웹 에이전트형 지식그래프 검증 기초 설계

1. 연구 배경: 자동검사는 판단의 자동화가 아니라 검증 기준의 실행 구조화

지식그래프의 규모가 커질수록 모든 Claim을 사람이 동일한 방식으로 반복 확인하는 것은 어렵다.
이에 따라 검증 과정에서 반복적으로 확인할 수 있는 조건을 규칙으로 표현하고,
기계가 검토 후보를 찾아내도록 하는 자동검사 구조가 필요하다.

여기서 자동검사는 역사적 사실에 대한 판단 자체를 기계에 맡긴다는 의미가 아니라,
사람이 채택한 검증 기준을 정규식, 스크립트, SPARQL 등의 기계 실행 가능한 형태로 구체화하고, 데이터에 반복적으로 적용하는 과정을 의미한다.

따라서 전체 검증 구조는 다음과 같이 구분된다.

사람이 검증 기준을 채택·승인
→ 기계가 구조적 조건을 반복 검사
→ 검토 후보 제시
→ 사람이 의미적 관계와 사료 내용을 판단
→ 판단 결과를 권고 형태로 기록

이 구조에서 중요한 것은 자동검사 결과가 곧바로 데이터 변경으로 이어지지 않는다는 점이다.

이와 관련하여 v9 계열에서는 review_flag와 claimDecision이 서로 다른 의미를 갖는다.
review_flag는 어떤 부분을 주의해서 검토해야 하는지를 나타내며,
core와 hold는 현재 데이터셋에서 해당 Claim을 어떻게 처리할 것인지를 나타낸다.
따라서 review flag가 존재한다고 해서 자동으로 Claim을 보류하거나 삭제하는 구조는 아니다.

참고 : SPARQL = SPARQL Protocol and RDF(Resource Description Framework) Query Language
즉, 스파클은 시맨틱 웹 표준 데이터 형식에서 데이터를 조회하고 조작하기 위해 사용하는 그래프 DB 전용 질의 언어다.

2. 자동화의 범위와 인간 판단의 범위

검증 과정에서 모든 조건을 같은 수준으로 자동화할 수 없다.
특히 '구조 규칙 적용'만으로 검증할 수 있는지 아닌지에 따라 수준이 달라질 수 있다.

이를테면 다음과 같은 조건은 비교적 구조적으로 표현할 수 있다.

  • 동일 Claim의 중복 여부
  • 동일 subject/object/relation을 가진 Claim의 존재 여부
  • 서로 다른 relation을 가진 Claim의 존재 여부
  • 필수 속성의 누락 여부
  • 관계 대상 URI의 존재 여부
  • 특정 값의 형식 오류 여부

반면 다음과 같은 문제는 단순한 구조 규칙만으로 확정하기 어렵다.

  • 서로 다른 relation이 실제로 같은 역사적 사건을 가리키는가
  • 두 사료가 같은 사건을 서로 다르게 기술한 것인가
  • 두 서술이 서로 모순되는가
  • 두 Claim을 하나로 병합해야 하는가
  • 동일 사건이지만 서로 다른 측면을 기술하는 것인가

따라서 본 연구의 MOCKUP은 자동탐지와 인간 검토를 분리하는 구조를 채택하였다.

이는 자동화의 범위를 축소하기 위한 것이 아니라,

역사자료 검증에서 기계가 안정적으로 수행할 수 있는 구조적 판단과 연구자의 해석이 필요한 의미적 판단을 구분하기 위함이다.

3. 설계 과정

이번 MOCKUP은 한 번에 완성된 결과물이 아니라 검증 구조를 단계적으로 구체화한 결과이다.

1차 완성한 검증용 HTML 초안에서는 자동검사와 검토 화면의 기본적인 구조를 적용했고,
이후 실제 v9.5 보고서에 포함된 Claim을 이용하여 Rule A/B, 인간 검토 단계, 권고 기록 및 구현 범위를 보다 명확하게 구분한 개선 MOCKUP을 구성하였다.

따라서 이 문서에서 설명하는 관계는 다음과 같이 이해할 수 있다.

검증 기준과 자동화의 한계를 설계 과정에서 검토
→ 9월 20일 전후의 초기 목업 1차 완성본
→ 검토 과정에서 규칙과 인간 판단의 경계 정리
→ 9월 28일 개선 MOCKUP 최종 완성본

중요한 점은 모든 원칙이 MOCKUP 실행을 통해 발견된 것은 아니라는 것이다.
일부는 v9.5 검토 자료와 기존 설계 내용을 검토하는 과정에서 도출한 설계 원칙(design commitment)이며,
실제 실행을 통해 검증된 결과와 구분해야 한다.

4. 「사료 대조 검토대장」 MOCKUP의 목적

우선, 목업 이름은 임시로 작성했고, 대장의 뜻은 다음과 같다.

참고> 대장[臺帳]
: 어떤 근거가 되도록 일정한 양식으로 기록한 장부나 원부(原簿). [출처: 표준국어대사전]

9월 28일 최종본으로 완성한 「사료 대조 검토대장」은 단순한 화면 디자인이 아니라,
자동탐지 → 인간검토 → 권고기록이라는 검증 workflow를 화면 수준에서 구체화한 프로토타입이다.

화면에서는 다음 네 가지를 명확하게 분리한다.

  1. 기계가 탐지할 수 있는 후보
  2. 연구자가 의미적으로 판단해야 하는 질문
  3. 판단 결과에 따른 권고
  4. 기존 Claim 데이터에 실제 변경을 가하지 않는다는 점

따라서 현재 MOCKUP을 실제 자동검사 시스템이라고 부르는 것은 정확하지 않다.

현재 화면의 SPARQL은 실제 실행되는 쿼리가 아니라
탐지 규칙의 구조를 보여주는 의사코드[Pseudocode: 알고리즘이나 로직의 흐름을 알기 쉽게 작성한 가상의 코드]이며,
실제 배치 실행, CSV/TTL 갱신, 영구 감사 로그, 외부 사료 검색, LLM 기반 의미 판단 등은 구현 범위에 포함되어 있지 않다.

5. Rule A: 서로 다른 관계 유형을 가진 Claim의 탐지

Rule A는 동일한 item 안에서 서로 다른 relation을 가진 Claim을 찾아내는 구조이다.

개념적으로 다음과 같은 조건을 표현한다.

SELECT ?item ?c1 ?r1 ?c2 ?r2 WHERE {
  ?c1 prov:belongsToItem ?item ;
      prov:hasRelation ?r1 .
  ?c2 prov:belongsToItem ?item ;
      prov:hasRelation ?r2 .
  FILTER(?c1 != ?c2 && ?r1 != ?r2)
}

이 규칙의 목적은 “서로 다른 관계가 존재한다”는 구조적 차이를 찾아 연구자가 검토할 후보를 확보하는 것이다.

그러나 이 규칙이 발견한 모든 사례가 오류인 것은 아니다.

v9.5 TTL의 구조를 기준으로 보면 동일 item 안에서도 다음과 같은 서로 다른 relation 조합이 존재한다.

  • CLM-006 / CLM-006-DATE
  • CLM-KIM-01 / CLM-KIM-02
  • CLM-LEE-A / CLM-LEE-B

이러한 사례는 서로 다른 관계를 표현한다고 해서 곧바로 잘못된 Claim이라고 볼 수 없다.

즉, Rule A는 오류 탐지 규칙이라기보다 관계 차이를 이용한 검토 후보 생성 규칙으로 보는 것이 적절하다.

또한 현재 pseudo-SPARQL은 양방향 조합을 모두 반환할 수 있으므로 동일한 Claim 쌍이 중복 후보로 나타날 가능성도 있다.

따라서 Rule A의 기술적 자동화 가능성과 검토 효율성은 구분해야 한다.

Rule A는 기계적으로 구현 가능한 조건이다.
그러나 현재 규칙 자체의 정밀도가 높다고 검증된 것은 아니다.

6. Rule A에서 오산학교 사례가 갖는 의미

오산학교 사례는 Rule A의 적용 범위를 보여주는 중요한 예이다.

CLM-OSAN-01과 CLM-OSAN-02는 각각 서로 다른 item에 속한다.

  • CLM-OSAN-01: 이승훈이 오산학교를 설립하였다.
  • CLM-OSAN-02: 이승훈이 오산학교를 개교하였다.

따라서 현재 Rule A의 prov:belongsToItem ?item 조건을 그대로 적용하면 이 두 Claim은 같은 item 안에 있지 않기 때문에 자동 탐지 대상이 되지 않는다.

이 점은 Rule A가 모든 관계 차이를 찾아내는 규칙이 아니라는 것을 보여준다.

다만 이 사실 역시 실제 SPARQL 엔진에서 실행하여 확인한 결과가 아니라, 현재 MOCKUP의 규칙과 Claim 구조를 대조하여 판단한 결과이다.

따라서 현재 단계에서는 다음과 같이 표현하는 것이 정확하다.

Rule A는 동일 item 내부의 관계 차이를 탐지하도록 설계되었으며, 서로 다른 item에 분산된 관계 차이는 현재 규칙의 범위 밖에 있다.

이후 'item 간 관계를 함께 검토할 것인지' 혹은 '별도의 Rule을 추가할 것인지'는 후속 설계 과제로 남는다.

7. Rule B: 동일 subject·object·relation을 가진 Claim 탐지

Rule B는 서로 다른 Claim이 동일한 subject, object, relation을 갖는 경우를 찾는 구조이다.

SELECT ?c1 ?c2 WHERE {
  ?c1 prov:hasSubject ?s ;
      prov:hasObject ?o ;
      prov:hasRelation ?r .
  ?c2 prov:hasSubject ?s ;
      prov:hasObject ?o ;
      prov:hasRelation ?r .
  FILTER(?c1 != ?c2)
}

이 규칙은 동일한 의미 구조를 가진 Claim이 여러 개 존재하는지를 찾는 데 사용할 수 있다.

현재 MOCKUP에서는 CLM-002와 CLM-011의 대성학교 사례가 이 구조의 예로 제시된다.

두 Claim은 모두 안창호와 대성학교 사이의 설립 관계를 표현하지만 서로 다른 Claim ID와 출처를 갖는다.

그러나 이 역시 자동으로 “중복 오류”라고 판정해서는 안 된다.

두 출처가 서로 다른 Evidence를 제공하고 있다면,
하나의 Claim에 복수 Evidence를 연결하는 방식과 별도의 Claim으로 유지하는 방식 사이에서 연구자의 판단이 필요할 수 있다.

따라서 Rule B의 역할은 중복 가능성이 있는 Claim을 찾는 것이며,
실제 병합 여부는 인간 검토 단계에서 결정하도록 설계하였다.

8. 인간 검토 1단계: 동일 사건 여부

자동탐지 이후 화면에서는 먼저 다음 질문을 제시한다.

이 두 Claim은 같은 사건을 가리킵니까?

선택지는 다음과 같다.

  • SAME: 같은 사건으로 보임
  • DIFFERENT: 별개의 사건으로 확인
  • UNCERTAIN: 여전히 불확실

이 단계는 관계 유형이 다르다는 이유만으로 두 Claim을 충돌 관계로 취급하지 않기 위한 것이다.

예를 들어 “설립”과 “개교”는 서로 다른 relation이지만,
실제 역사적 사건의 관계를 어떻게 정의했는지에 따라 같은 사건의 서로 다른 서술일 수도 있고 별개의 사건일 수도 있다.

따라서 먼저 사건의 동일성을 판단한 다음 출처 간 양립성을 검토하는 순서가 필요하다.

9. 인간 검토 2단계: 출처 간 양립성

두 Claim이 같은 사건을 가리킨다고 판단된 경우에만 다음 질문으로 이동한다.

두 출처의 내용은 서로 양립 가능합니까?

선택지는 다음과 같다.

  • CONFLICT: 양립 불가
  • COMPATIBLE: 양립 가능
  • UNCERTAIN: 판단 보류

이 단계의 핵심은 SAME이라는 판단이 곧 CONFLICT를 의미하지 않는다는 점이다.

같은 사건을 서로 다른 표현으로 설명하는 것은 가능하다.

반대로 동일 사건에 대해 서로 양립할 수 없는 날짜나 관계를 제시한다면 출처 충돌 검토가 필요할 수 있다.

따라서 이 MOCKUP에서는

사건 동일성 → 출처 양립성

이라는 두 단계의 판단 구조를 분리하였다.

10. 중복 Claim의 처리

동일 subject·object·relation을 가진 Claim이 발견된 경우에도 자동 병합하지 않는다.

화면에서는 다음과 같은 선택지를 제공한다.

  • MERGE: 하나의 Claim으로 병합 권고
  • KEEP_SEPARATE: Evidence를 각각 보존하고 별도 Claim 유지 권고
  • MERGE_DEFERRED: 추가 확인 후 판단

이는 Claim과 Evidence의 관계를 보존하기 위한 설계이다.

특히 CLM-002와 CLM-011처럼 서로 다른 출처가 동일한 관계를 기술하는 경우,
단순히 문자열이 같다는 이유만으로 하나를 삭제하면 각각의 출처와 Evidence에 관한 provenance 정보가 약화될 수 있다.

(달리 말해, 텍스트가 똑같다고 해서 단순히 중복으로 보고 하나를 지워버리면,
각 주장이 가지고 있던 고유한 출처나 뒷받침 증거를 잃어버리게 되어 데이터의 신뢰성과 추적 기능이 떨어질 수 있다.)

따라서 자동검사는 중복 가능성을 제시하되, 병합은 연구자가 결정하도록 하였다.

11. change_history에 관한 주의점: 실행 결과가 아니라 설계상의 주의점

자동화와 관련하여 change_history를 주의해야 한다.

기존 검토 자료에서는 change_history에 자연어로 기록된 내용이 존재한다.
(관련해서 V9_5.ttl 트리플 prov:changeHistory를 확인해 볼 수 있다.)

이러한 기록에는 실제 변경 이력, 기존 판정의 근거, 후속 검토 사유 등이 함께 나타날 수 있기 때문에
단순한 문자열 규칙만으로 그 의미를 확정하기 어렵다.

따라서 본 연구에서 도출한 원칙은 “change_history를 실제 자동검사하여 오탐을 확인했다”는 것이 아니다.

현재 MOCKUP에는 change_history를 대상으로 하는 자동검사 규칙이나 시험이 구현되어 있지 않다.

오히려 v9.5 자료를 검토하고 검증 workflow를 설계하는 과정에서 다음과 같은 주의점이 도출되었다.

자연어로 기록된 변경 이력은 단순한 오류 메시지와 동일하게 취급해서는 안 되며,
자동화 대상이 되더라도 우선 검토 후보로 다루고 최종 의미 판단은 사람에게 남겨야 한다.

이 원칙은 MOCKUP의 구조에도 반영되어 있다.

즉,

자동탐지 → 인간 검토 → 권고 기록

이라는 구조를 사용하고, 자동검사 결과가 곧바로 claimDecision이나 changeHistory를 변경하지 않도록 하였다.

또한 CLM-OSAN-01과 같은 사례에서 review_flag, claim_status, claimDecision, changeHistory의 표현을 서로 구분해서 읽어야 한다는 점도 확인할 수 있다. v9 데이터 사전에서도 review_flag는 검토 대상이나 문제 유형을 나타내며, core/hold 결정과 자동으로 동일시되지 않는다.
(참고로, v9 데이터 사전 경우 v9_4에서 명시적으로 dict.csv 하나를 만들었는데, 과정이 번거로워져서 폐기했다. )

따라서 change_history의 자동화는 현재 MOCKUP에서 검증된 기능이 아니라 향후 자동화 시 주의해야 할 설계 과제로 위치시키는 것이 정확하다.

12. Hard-fail 방식의 한계

이러한 구분은 hard-fail 방식과도 연결된다.

참고> Hard-fail:
규칙에 안 맞으면 무조건 오류로 딱 잘라내는 방식.
글이나 맥락처럼 정답이 애매한 것에는 유연하게 대처하지 못하고 융통성 없이 차단해 버린다.

구조적으로 명확한 조건에서는 위반을 즉시 오류로 처리할 수 있다.
예를 들어 필수 속성이 반드시 존재해야 하는 경우에는 해당 조건을 만족하지 않으면 오류로 표시하는 방식이 가능하다.

그러나 자연어 기반 변경 이력이나 역사적 관계의 의미 해석에서는 같은 방식으로 처리하기 어렵다.

따라서 향후 자동검사 체계에서는 최소한 다음과 같은 수준을 구분할 필요가 있다.

수준 의미 처리
Violation 구조적 조건을 명백하게 위반 오류/차단 후보
Warning 추가 검토가 필요한 조건 인간 검토
Info 참고할 만한 구조적 특성 정보 제공

이러한 구분은 향후 SHACL 기반 검증으로 확장할 경우에도 연결할 수 있다.

v9.5의 후속 설계에서 SHACL shape 작성을 고려한 만큼,
현재 MOCKUP의 “자동검사와 인간 검토의 구분”을 실제 검증 레이어로 발전시키는 방향으로 활용할 수 있다.
(다만, SHACL(Shapes Constraint Language) Shape 경우 필자가 잘 몰라서 자세히 안 다뤘고,
일단 자동 검사 레이어 (예> pyshacl 엔진 구동)에 층위 하나 더 쌓는 개념으로 접근했다.
특히 SHACL Shape를 작성할 때 심각도[Severity, sh:severity]를 지정할 수 있는 기능이 있기에
sh:Violation (위반 / 에디터 오류): sh:Warning (경고): sh:Info (정보):이 기능을 사용하고자 했다.)

13. 사람이 먼저 정의한다는 표현의 수정

verification_report_v9_5.md 자동검사에 관한 설명에서
“검증 기준은 먼저 사람이 정의한다”는 표현은 다소 단순화되어 있다.

참고> 관련 원문은 다음과 같다.

기존 자동검사
: 그동안 보고서에서 '자동검사', '재검증', '재검사' 등의 표현을 사용해 왔는데, 여기서 말하는 자동검사는 검증의 판단 자체를 자동화한다는 의미라기보다, **사람이 이미 정의한 검증 기준을 정규식이나 스크립트 등의 형태로 표현하여 반복적으로 검사할 수 있도록 만드는 것**에 가깝다.

실제 연구 과정에서는 검증 규칙 후보가 먼저 고려 혹은 제안되고,
연구자가 이를 검토하여 채택하거나 기각하는 과정도 포함된다.
v9.5에서 이루어진 규칙 검토와 기각 역시 이러한 과정을 보여준다.

따라서 본 연구에서 인간의 역할은 단순히 규칙을 처음부터 작성하는 것이라기보다,

검증 규칙 후보를 검토하고, 채택·수정·기각하며, 최종적으로 사용할 기준을 승인하는 것

으로 정의하는 것이 더 정확하다.

이는 웹 에이전트 환경에서 특히 중요하다고 생각한다.
이렇게 접근해야 향후 AI가 연구자에 의한 학습을 바탕으로 규칙 후보를 생성하더라도
그 규칙이 역사자료의 의미에 적절한지 판단하고 최종 승인하는 연구자의 역할이 더 선명히 남을 것이다.

14. MOCKUP 내역과 설계상 규칙 구분

현재 MOCKUP에서 모든 원칙을 실증(구현)했다고 표현해서는 안 되며,
다음 내역을 구분해야 한다.

데이터 구조를 대조하여 확인한 사항

  • CLM-OSAN-01과 CLM-OSAN-02는 서로 다른 item에 속한다.
  • 동일 item 내에서도 서로 다른 relation을 가진 정상적인 복수 Claim 사례가 존재한다.
  • CLM-002와 CLM-011은 동일 subject/object/relation 구조를 가진 서로 다른 Claim이다.
  • review_flag와 claimDecision은 동일한 의미의 상태값이 아니다.

MOCKUP의 설계로 반영한 사항

  • 자동탐지 결과를 즉시 오류로 확정하지 않는다.
  • 사건 동일성과 출처 양립성을 두 단계로 분리한다.
  • 중복 Claim을 자동 병합하지 않는다.
  • 판단 버튼은 실제 CSV/TTL을 변경하지 않고 권고를 기록한다.
  • 자연어 기반 판단은 인간 검토 단계에 남긴다.

아직 실행하여 검증하지 않은 사항

  • 실제 SPARQL 실행 성능
  • Rule A/B의 실제 precision/recall
  • 대규모 데이터에서의 중복 후보 발생량
  • 실제 배치 자동검사
  • SHACL 기반 검증 실행
  • LLM의 의미적 판정
  • 외부 사료 자동 검색
  • CSV/TTL 자동 갱신
  • 영구 감사 로그 저장

즉, 이번 MOCKUP은 “자동검사 정확도를 검증했다”고 할 수 없고,
검증 workflow와 자동화 경계를 설계하고 구체화했다고 표현하는 것이 타당하다.

15. 웹 에이전트와의 연결: 기초 설계 단계

이러한 구조는 향후 웹 에이전트가 수행할 수 있는 작업 흐름과 연결될 수 있다.

웹 에이전트는 단순히 화면을 생성하는 것이 아니라 주어진 목표에 따라 데이터를 탐색하고, 규칙을 실행하고, 필요한 정보를 수집하며, 사용자의 판단을 요청하는 workflow를 구성할 수 있다.

현재 MOCKUP은 이러한 전체 에이전트를 구현한 것은 아니다. 그러나 다음과 같은 기본 workflow를 설계했다는 점에서 웹 에이전트형 검증 구조의 기초 단계로 볼 수 있다.

자연어로 표현된 검증 의도
↓
검증 규칙의 구조화
↓
그래프 데이터에서 검토 후보 탐지
↓
인간 연구자에게 의미 판단 요청
↓
판단 결과를 권고 형태로 기록

여기서 중요한 것은 “자연어를 기계어로 번역했다”는 식의 표현이 아니다.

보다 정확하게는,

"자연어로 표현된 검증 의도를 기계가 반복 실행할 수 있는 구조적 규칙으로 구체화하였다"

16. Neo4j와 그래프 기반 에이전트의 연결

그래프 데이터베이스는 사람·기관·사건·관계·출처 사이의 연결 구조를 질의하는 데 적합하며,
이러한 구조는 향후 Graph RAG나 AI agent와 결합할 수 있다.

본 연구에서 필자의 Neo4j 관련 학습 이력은 이러한 그래프 질의 및 그래프 기반 AI 활용에 관한 기술적·개념적 배경을 제공하였다.

다만 현재 「사료 대조 검토대장」 MOCKUP의 Rule A/B가 Neo4j에서 실제 실행된 것은 아니다.

화면의 규칙은 SPARQL 형태의 의사코드[Pseudocode: 알고리즘이나 로직의 흐름을 알기 쉽게 작성한 가상의 코드]로 표현되어 있으며, 현재 단계에서는 그래프 기반 검증 workflow를 어떻게 구조화할 것인가를 보여주는 설계 모델로 이해해야 한다.

향후에는 동일한 검증 규칙을 RDF/SPARQL과 Neo4j/Cypher 환경에서 각각 구현하여, 데이터 구조에 따른 탐지 방식과 확장성을 비교할 수 있다.

17. 자동화 가능 범위와 향후 연구

현재 단계에서 검증 workflow를 다음과 같이 정리할 수 있다.

검증 작업 자동화 가능성 현재 상태 인간 판단
동일 subject/object/relation 탐지 구조적으로 높음 Rule B로 설계 필요
동일 item 내 relation 차이 탐지 구조적으로 가능 Rule A로 설계 필요
필수 속성 누락 검사 높음 후속 구현 가능 case by case
URI/관계 대상 존재 여부 높음 후속 구현 가능 제한적
동일 사건 여부 낮음 UI 질문으로 설계 필수
출처 간 양립성 낮음 UI 질문으로 설계 필수
Claim 병합 여부 낮음 권고 선택으로 설계 필수
change_history 의미 판독 제한적 미구현 필수
SHACL 기반 구조 검증 높음 후속 과제 심각도에 따른 필요
외부 사료 검색 별도 구현 필요 미구현 필요
LLM 기반 의미 판단 별도 구현 필요 미구현 최종 승인 필요

여기서 Rule A/B의 “자동화 가능”은 규칙을 기계 실행 가능한 형태로 표현할 수 있다는 뜻일 뿐, 현재 규칙의 정확도나 실무적 효율성이 검증되었다는 의미가 아니다.

특히 Rule A는 정상적인 복수 관계도 후보로 포함할 수 있으므로 향후에는 중복 후보 제거, 사건 범위 정의, 관계 유형별 필터링 등의 정밀화가 필요하다.

18. 연구 방법론적 의미

이번 MOCKUP의 의미는 자동화 자체보다는 역사자료 검증에서 무엇을 자동화하고 무엇을 인간에게 남길 것인지 명시적으로 분해했다는 점에 있다.

첫째, 구조적으로 표현할 수 있는 차이는 규칙으로 만들 수 있다.

둘째, 규칙이 탐지한 차이는 곧 오류가 아니다.

셋째, 역사적 사건의 동일성이나 사료 간 양립성처럼 의미 해석이 필요한 문제는 인간 검토 단계로 이동해야 한다.

넷째, 인간의 판단 역시 실제 데이터 변경과 분리하여 우선 권고 형태로 기록할 수 있다.

이 구조는 자동화를 “인간 판단의 대체”가 아니라 인간 판단이 필요한 지점을 더 명확하게 드러내는 검증 보조 체계이다.

19. 결론

이번 연구에서 만든「사료 대조 검토대장」 MOCKUP은 지식그래프의 역사적 Claim을 자동으로 판정하는 시스템이 아니다.

현재 구현 수준에서는 실제 SPARQL 실행, 배치 자동검사, CSV/TTL 자동 갱신, 영구 감사 로그, 외부 사료 검색 및 LLM 기반 의미 판단이 구현되어 있지 않다.

대신 본 MOCKUP은 다음의 검증 workflow를 구체적인 화면 구조로 표현하였다.

검증 규칙 후보의 채택·구조화
→ 구조적 검토 후보 탐지
→ 인간의 사건 동일성 판단
→ 출처 간 양립성 판단
→ 병합 또는 유지에 대한 권고
→ 감사 가능한 기록

Rule A와 Rule B는 이 workflow에서 기계가 수행할 수 있는 구조적 탐지의 예시이며,
Rule A가 보여주듯 관계 차이를 탐지하는 것과 역사적 오류를 판정하는 것은 동일하지 않다.

그렇기에 자동탐지는 검토 대상을 생성하는 단계로 한정하고,
사건의 동일성·출처의 양립성·Claim 병합과 같은 판단은 인간 검토 단계에 남겨두었다.

특히 change_history와 같은 자연어 기록은 MOCKUP에서 실제 자동검사를 수행한 대상이 아니며,
현재 구조에서는 자동 검사(변경) 대신 인간 검토와 권고 기록의 형태로 반영하였다.

따라서 이번 작업은 완성된 웹 에이전트의 구현이라기보다, 지식그래프 검증 업무를 향후 웹 에이전트가 수행할 수 있는 구조적 workflow로 분해하고, 그중 자동화 가능한 영역과 인간의 의미 판단이 필요한 영역을 구분한 기초 설계로 보는 것이 적절하다.

향후에는 Rule A/B를 실제 SPARQL 또는 Cypher로 실행하여 탐지 결과를 정량적으로 비교하고, SHACL을 이용한 구조 검증과 심각도별 처리 체계를 구축하며, 외부 사료 검색과 LLM 기반 후보 설명 기능을 추가할 수 있다.

그럼에도 최종적인 역사적 판단과 데이터 변경 승인에는 연구자의 검토 절차를 유지하는 것이 본 검증 구조의 핵심 원칙이 될 것이다.

20. 참고> 프로젝트 전체 설계와 검증 MOCKUP의 관계

이번 검증 workflow는 본 프로젝트가 지향하는 재현성과 검증 가능성의 확보와도 연결된다.
본 프로젝트에서 온톨로지 구축은 개별 연구자의 작업에서 출발하지만,

  • 그 결과물이 후속 연구자에 의해 검토되고 확장되기 위해서는 어떤 관계를 왜 설정했는지,
  • 해당 주장을 어떤 출처와 근거를 통해 구성했는지,
  • 그리고 불확실한 부분을 어떻게 처리했는지를 추적할 수 있어야 한다.

메인 Event 온톨로지가 인물·사건·관계를 구조화하는 역할을 담당한다면,

Provenance 트랙과 검증 MOCKUP은 그 구조에 포함된 주장과 근거를 검토하고 기록하는 절차를 구체화한다.

따라서 이번 MOCKUP은 단순한 UI 실험이 아니라,

개별 연구자의 온톨로지 구축 결과를 다른 연구자가 재검토하고 후속 작업으로 확장할 수 있도록 하는 검증 가능한 연구 workflow의 한 부분으로 볼 수 있다.
