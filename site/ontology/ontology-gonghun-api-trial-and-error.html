공훈전자사료관 API 연동 시행착오: v6 → v10 [26.09.21 재확인ver.]

2026-09-09 첫 작성 · 2026-09-14 최종 갱신(전체 순회 중 XML 파싱 오류로 재중단 내용 포함) · v6_with_gonghun ~ v10 전 과정 기록
#온톨로지 #공훈전자사료관 #API #CORS #XML파싱 #시행착오

1. 이 기록이 필요한 이유

국가보훈부 공훈전자사료관 오픈API로 온톨로지 인물과 독립유공자 포상 기록을 대조하는 기능은, v6에 처음 추가된 뒤 v10까지 여섯 차례 손을 봤는데도 실제 배포 환경에서 한 번도 끝까지 제대로 동작한 적이 없다. 매번 "고쳤다."라고 생각했지만 원인이 계속 바뀌었다 — 필드명 버그 → 프로토콜 문제(mixed content) → 프록시 불안정 → API 자체의 가용성 문제 → 이름 필터 파라미터 무시 → 그리고 이번엔 서버가 내려주는 XML 자체의 결함. 이 각각을 어떻게 알아냈고 무엇을 시도했다 실패했는지 시간순으로 남겨야, 다음에 또 "왜 안 되지"부터 다시 시작하지 않는다.

2. v6_with_gonghun — 최초 구현, 미검증 상태로 배포

처음 만들 때 코드는 다음과 같이 이름을 읽었다. 

var name = (rec["성명"] || rec["name"] || "").trim();

이때 화면에는 "이 호출이 실제로 성공하는지 사전에 검증하지 못했습니다. 대부분의 정부 사이트는 CORS를 차단하므로 실패할 가능성이 있습니다"라는 설명을 넣었다 — 실행 가능한 코드를 실제로 실행해보지 않고 배포한 것을 숨기지 않기 위해서였다.

3. 안내 문구 수정 — "직접 실행해보니 호출은 됐다"

이후 직접 실행해보니 호출 자체는 됐길래, 그 취지로 안내 문구를 바꿨다. 문구는 "실행할 때는 호출이 되었습니다. 실패할 경우 오류 내용을 확인해 다시 살펴보겠습니다"로 교체했다. 이 시점까지는 필드명 버그(성명/name)가 그대로 남아 있었다는 걸 몰랐다 — 호출 자체(네트워크 요청)는 됐어도, 응답에서 이름을 못 읽으니 매칭은 어차피 0건이었을 것이다.

4. v8_with_gonghun — 같은 버그를 그대로 계승

v8로 데이터가 바뀌면서 온톨로지 쪽 로직은 전부 다시 짰지만, 공훈 연동 부분은 v6 코드를 그대로 복사해 왔다. 즉, 필드명 버그도 그대로 옮겨왔다는 뜻이다. 이 시점까지 실제 테이블을 열어 "0명 매칭"인지 확인하지 않았다. (코드를 짜는 필자도, 검증하는 클로드도 매칭 확인 x 이 저장소 readme에도 나오듯 시각화는 주로 클로드 이용했고, 로직은 거의 다 본인이 고려 & 구현한 건데, 위와 같은 소소한 문제 때문에 AI 코드를 계속 재검증하는 것이다.)

5. 실제 화면에서 "전원 0명 매칭" 확인, 원인 추적 시작

스크린샷으로 "v5 인물 30명 중 0명 매칭"이 처음 보고됐다. 이때부터 실제 API 문서를 찾아 나섰다.

국가보훈부 공식 문서(mpva.go.kr)를 찾아 확인한 결과, 응답 필드는 성명/name이 아니라 NAME_KO였다. 게다가 코드 주석에 "이름 필터 파라미터가 공식 문서로 확인되지 않는다"고 적혀 있었는데, 실제로는 nameKo라는 이름 검색 파라미터가 공식 문서에 명시돼 있었다.

실제 API를 호출해 응답 구조를 직접 확인했다 — 훈격은 HUNKUK, 운동계열은 WORKOUT_AFFIL, 공적개요는 ACHIVEMENT였다. 전부 처음부터 잘못 짐작한 필드명이었다. (즉, 처음에 제대로 못 했다는 말)

6. v10 — 필드명 전면 수정 + nameKo 직접조회로 재작성

19,059명 전체를 페이지 단위로 훑던 방식을, nameKo 파라미터로 인물 20명(v9.5 Claim 스키마 기준)에 대해 각각 직접 질의하는 방식(20회 요청)으로 바꿨다. jsdom과 실제 API 응답 구조를 흉내낸 모의 데이터로 매칭·동명이인·미매칭 세 경우가 정확히 집계되는 것까지 배포 전에 확인했다.

7. 배포 후 전원 "Failed to fetch" — mixed content 진단

*참고* 아래 내용부터는 필자도 잘 모름. 실습용 API는 늘 잘 호출되었기에 이런 거 생각해 볼 필요 없었음.// 실제 배포 환경(Render, HTTPS)에서 여전히 20명 전원이 실패했다. "Failed to fetch"는 요청이 서버에 닿기도 전에 브라우저가 막았을 때 나오는 전형적인 메시지다. 확인해보니 원인은 필드명이 아니라 프로토콜이었다 — 공훈전자사료관 API는 HTTP만 제공하는데 (https://로 접속하면 API가 아닌 404 오류 페이지가 뜬다), 이 사이트는 HTTPS로 배포돼 있어 브라우저가 혼합 콘텐츠(mixed content)로 요청 자체를 차단한 것이었다. 코드 버그가 아니라 애초에 브라우저 보안 정책상 막힐 수밖에 없는 조합이었다.

8. HTTPS 프록시 폴백 추가 — 그러나 이것도 실패

직접 호출이 막히는 상황을 우회하기 위해, HTTPS로 감싸주는 공개 프록시 (allorigins.win, codetabs.com) 순차 폴백을 추가했다. 재배포 후 확인한 결과는 이랬다.

  • 직접 호출: 여전히 Failed to fetch (예상대로)
  • 프록시1(allorigins): Failed to fetch
  • 프록시2(codetabs): 일부는 HTTP 408(타임아웃), 일부는 Failed to fetch

HTTP 408은 연결 자체는 됐지만 응답이 늦어 타임아웃났다는 뜻이라, 프록시가 정부 서버까지는 도달했지만 그 뒤가 느리거나 막혔다는 정황이다. 무료 공개 프록시는 무보증 서비스라 이 정도 불안정성은 예견됐던 일이지만, 실제로 재현되는 걸 보고 이 경로 자체를 신뢰할 수 없다고 판단했다.

9. 다시 직접 재호출 — API 자체가 그새 접근 불가로 바뀜

*거듭 언급하지만, 필자는 이런 경우를 이번에 처음 봄.* 프록시 우회가 안 되니, 같은 API를 다시 직접 호출해봤다. 몇 시간 전 같은 방식으로 성공했던 바로 그 요청이, 이번엔 실패했다 — http://로 요청해도 https://로 강제 리다이렉트되며 API가 아닌 404 오류 페이지가 돌아왔다. 즉 이 API는 "브라우저에서만 막히는" 게 아니라 시간대에 따라 아예 접근 자체가 불안정하다는 뜻이었다. 원래 성공했던 호출 방식이 몇 시간 뒤에 재현되지 않는다는 건, 이 API를 실시간 의존성으로 쓰는 설계 자체가 취약하다는 신호다.

10. 정적 스냅샷 방식으로 전환

브라우저 실시간 호출을 포기하고, 로컬 실행 스크립트 (gonghun_match.py)로 한 번 조회한 결과를 data/gonghun_snapshot.json에 저장해두고, 사이트는 그 정적 파일만 읽어오는 방식으로 바꿨다. Python의 urllib은 브라우저처럼 http를 https로 자동 승격하지 않으므로, 같은 API라도 로컬 환경에서는 이 제약 없이 호출할 수 있다는 점에 착안했다. 실시간 호출 버튼은 "실패 가능성이 높다"고 미리 고지한 채 접이식 보조 옵션으로만 남겼다.

11. 이번에도 실패 재현

배포 후 다시 확인했을 때도 "20명 호출 오류"가 그대로 나왔다. 다만 이 화면은 기본 스냅샷 경로가 아니라 접이식 "실시간 호출 다시 시도" 버튼을 눌렀을 때 나오는 화면과 같은 형태라, 정적 스냅샷 파일 (gonghun_match.py를 로컬에서 실행해 생성)이 아직 만들어지지 않은 상태에서 실시간 경로를 다시 시도한 결과일 가능성이 크다. 즉 이 실패 자체는 7~9번에서 이미 확인된 문제(mixed content + API 불안정)의 재현이지, 새로운 원인은 아니다.

12. nameKo 파라미터가 실제로는 서버에서 무시됨을 확인 — 전체 순회로 회귀

10번의 정적 스냅샷 스크립트(gonghun_match.py)를 실제로 로컬에서 실행해본 뒤, 또 하나의 사실이 드러났다. nameKo 파라미터는 공식 문서(mpva.go.kr)에는 분명히 나와 있지만, 서버가 실제로는 이 값을 무시한다는 것이다. nameKo에 어떤 이름을 넣어도 TOTAL_COUNT=19059가 그대로이고, 응답은 항상 가나다순 "가네코 후미코, 가재연, 가재창..."으로 시작하는 첫 페이지가 그대로 돌아왔다 — nameKo가 아예 없을 때와 결과가 완전히 동일했다. 즉 6번에서 "이름별 직접 질의(20회)"로 전환한 설계 자체의 전제(서버가 이름으로 필터링해준다)가 틀렸던 것이다.

이에 따라 스크립트는 전체 순회 방식으로 되돌아갔다 — 다만 v6/v8과는 다르게, 이번엔 필드명(NAME_KO)이 이미 바로잡힌 상태로 되돌아간 것이다. nCountPerPage=50으로 전체 약 19,059명(≈382페이지)을 처음부터 끝까지 훑으면서, 각 페이지에서 20명의 NAME_KO와 정확히 일치하는 레코드만 그때그때 수집한다. 서버의 이름 필터가 작동하든 안 하든 결과가 항상 정확하도록, 필터링을 서버에 의존하지 않고 클라이언트 (스크립트) 쪽에서 전량을 직접 대조하는 방식으로 바꾼 것이다.

전체 순회라 요청 수가 많아진 것(약 382회)을 감안해 다음을 함께 추가했다.

  • 요청 사이 0.3초 간격 유지(정부 서버에 대한 최소한의 예의)
  • 페이지별 실패 시 최대 3회까지 점증 대기 후 재시도
  • 20페이지마다 체크포인트(gonghun_match.checkpoint.json) 저장 — 중간에 중단돼도 다음 실행 시 이어서 재개 가능
  • 중단 시에도 그 시점까지 수집된 결과로 스냅샷을 일단 저장(부분 결과라도 남긴다)
정리하면: 6번의 "인물별 직접 질의 20회"는 서버가 이름 필터를 지원하지 않는다는 걸 몰랐던 상태에서 나온 설계였고, 실제로 로컬에서 돌려보고서야 그 전제가 틀렸다는 게 드러났다. 이 프로젝트에서 반복돼온 패턴 — "문서에 쓰여 있다고 실제로 그렇게 동작하는 건 아니다, 결국 직접 실행해봐야 안다" — 이 여기서도 그대로 재현됐다.

13. 전체 순회 실행 — 페이지 140에서 XML 파싱 오류로 재중단

12번의 전체 순회 스크립트를 실제로 로컬에서 실행했다. 진행 로그는 다음과 같았다. 

  [137/382] 페이지 처리 완료 — 누적 스캔 6850건, 지금까지 매칭된 인물 1/20명
  [138/382] 페이지 처리 완료 — 누적 스캔 6900건, 지금까지 매칭된 인물 1/20명
  [139/382] 페이지 처리 완료 — 누적 스캔 6950건, 지금까지 매칭된 인물 1/20명

중단됨: 페이지 140 호출 3회 모두 실패: reference to invalid character number: line 266, column 159
현재까지 결과를 스냅샷으로 저장하고, 체크포인트를 남깁니다.

139페이지(약 6,950건, 전체의 36%가량)까지는 정상적으로 진행됐다 — 요청 간격·재시도 로직 자체는 의도대로 동작했고, 체크포인트와 부분 저장도 설계대로 남았다. 문제는 그 다음이다.

reference to invalid character number는 네트워크 오류나 타임아웃이 아니라, 서버가 내려준 XML 응답 자체에 XML 명세상 허용되지 않는 문자 참조가 들어 있을 때 파서(Python xml.etree.ElementTree, 내부적으로 expat)가 던지는 오류다. 특정 레코드의 필드값(예: 공적개요나 이명 같은 자유서술 텍스트)에 제어문자 같은 값이 섞여 있고, 이게 XML로 직렬화되는 과정에서 &#N; 형태의 숫자 문자 참조로 나왔는데 그 N이 XML이 허용하는 문자 범위(#x9, #xA, #xD, #x20~#xD7FF 등)를 벗어난 것으로 보인다. 즉 이번 것은 요청이 실패한 게 아니라, 서버가 "성공"으로 응답한 내용 자체가 XML 명세를 위반하는 경우다. (거듭 적지만, 필자는 이런 경우를 처음 봤다.)

이 지점에서 기존 재시도 로직의 전제가 잘못됐다는 게 드러났다. 최대 3회까지 점증 대기 후 재시도하도록 만들어뒀는데, 이 오류는 같은 페이지를 다시 요청해도 서버가 내려주는 데이터(그리고 그 안의 결함 있는 문자)가 똑같이 재현되는 결정론적 오류다 — 네트워크 지연이나 서버 과부하 같은 일시적 문제가 아니라, 그 페이지에 포함된 특정 레코드 하나가 원천적으로 깨져 있는 것이다. 그런데도 코드는 이를 여느 네트워크 오류와 똑같이 취급해 3번 재시도하고, 그래도 안 되면 전체 순회를 통째로 중단시켰다. 19,059명 중 레코드 하나(또는 몇 개)의 결함 때문에 나머지 수천 페이지를 아예 못 훑게 되는 구조였던 셈이다.

또한 이번 실행에서 139페이지까지 매칭된 인물이 1/20명에 그쳤는데, 이는 이상 징후가 아니라 가나다순 정렬의 특성으로 설명된다. v9.5 인물 20명 중 상당수가 성씨 "이"(이승훈·이시영·이종일·이종호·이회영· 이동휘·이승만, 7명)로, 한글 자모 순서상 중후반부(ㅇ)에 위치한다. 전체의 36%만 훑은 시점에서는 아직 그 구간에 도달하지 못했을 가능성이 커서, 매칭 수가 적은 것 자체는 정상 범위로 판단된다.

14. 지금까지의 결론 (갱신 & 26.09.21 본문 전체 재확인)

  • 필드명 버그(성명/name vs 실제 NAME_KO)는 확실히 고쳤고, 실제 API 문서 대조로 검증됐다.
  • 이 API는 HTTP 전용 + 접근 자체가 불안정하다는, 코드로는 해결할 수 없는 근본적 제약이 있다. 브라우저에서 실시간으로 호출하는 설계 자체를 재고해야 한다.
  • 공식 문서에 명시된 nameKo 이름 필터 파라미터도 실제로는 서버가 무시한다는 것을 로컬 실행으로 확인했다 — 문서와 실제 동작이 다를 수 있다는 걸 다시 한 번 확인한 사례.
  • 그래서 스크립트는 이름별 단건 질의(20회)가 아니라 전체 약 382페이지 순회 + 클라이언트 측 정확일치 필터링으로 되돌아갔다.
  • [갱신] 그런데 전체 순회 자체도 139/382페이지 지점에서 서버가 반환한 XML 응답 안에 XML 명세를 위반하는 문자 참조가 포함된 레코드 때문에 재차 중단됐다. 이는 네트워크·서버 지연 같은 일시적 문제가 아니라 데이터 자체의 결함이라 같은 요청을 몇 번을 재시도해도 재현되는 결정론적 오류이며, 현재 로직은 이 경우를 일반 오류와 구분하지 않고 3회 재시도 후 전체 순회를 중단시켜버린다는 설계상의 허점이 드러났다.
  • [갱신, 다음에 할 일] XML 파싱 오류(ET.ParseError)는 네트워크 오류와 별도로 잡아, 재시도 없이 해당 페이지만 건너뛰고 로그에 남긴 뒤 다음 페이지로 계속 진행하도록 고쳐야 한다. 정 안 되면 원본 바이트에서 XML이 허용하지 않는 제어문자를 순회 전에 한 번 걸러내는 전처리(sanitize) 단계를 추가하는 방법도 있다. 두 방법 중 어느 쪽이든, "레코드 하나의 결함이 전체 19,059명 조회를 멈춰서는 안 된다"는 원칙을 먼저 세우는 게 우선이다.
  • 가장 신뢰할 수 있는 경로는 여전히 로컬 스크립트로 미리 조회해 정적 스냅샷으로 배포하는 것이다 — 다만 이번 사례로, 그 로컬 스크립트조차 "정상 응답 = 파싱 가능한 XML"이라는 가정을 그대로 두면 똑같이 중간에 멈출 수 있다는 게 확인됐다. API가 살아있고 응답을 준다고 해서 그 응답이 항상 유효하다는 보장은 없다는 것도 함께 기록해둔다.
