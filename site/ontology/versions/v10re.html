01

탐지 계층 — 관계 검토 대상 Claim 목록

탐지 규칙 예시 · 실제 자동 실행(SPARQL 실행 기능) 미구현
아래 목록은 "둘 중 하나가 틀렸다"는 상충(conflict)이 아니라, 서로 다른 종류의 관계를 갖는 Claim 쌍이 발견됐으니 사람이 그 관계의 성격을 확정해 달라는 목록이다. hasReviewFlag(문제 신호)와 claimDecision (core/hold 처리 결과)은 이미 v9.3에서 끝난 판정이며, 이 화면은 그 판정을 뒤집는 곳이 아니라 그 판정을 유지할지, 관계 검토 결과를 어떻게 남길지에 대한 근거를 권고로 추가하는 곳이다. 성격이 다른 두 종류의 탐지 규칙(A/B)이 있고, 각 규칙은 서로 다른 처리 버튼 세트로 이어진다.
# 규칙 A — 같은 item에 서로 다른 relation을 가진 Claim이 존재 (관계 유형 상이 탐지)
PREFIX prov: <https://ontology.gwanhak-inmul.kr/prov#> SELECT ?item ?c1 ?r1 ?c2 ?r2 WHERE { ?c1 prov:belongsToItem ?item ; prov:hasRelation ?r1 . ?c2 prov:belongsToItem ?item ; prov:hasRelation ?r2 . FILTER(?c1 != ?c2 && ?r1 != ?r2) }

⚠ 규칙 A는 같은 item 안에서 relation이 서로 다른 Claim을 찾는 규칙입니다. 여기서 item은 Claim을 인물·기관·사건별로 묶어 둔 단위입니다. 그런데 아래 오산학교 예시의 두 Claim은 서로 다른 item에 들어 있습니다. CLM-OSAN-01(이승훈이 오산학교를 설립)은 item-1에, CLM-OSAN-02(이승훈이 오산학교를 개교)는 item-20에 속합니다. 위 쿼리는 belongsToItem이 같은 Claim끼리만 비교하므로, 이 쿼리를 실제로 실행하면 이 쌍은 탐지되지 않습니다. 이 목업에서는 "같은 사건을 가리키는데 relation만 다른 사례"를 보여주기 위해 이 쌍을 수동으로 목록에 넣었습니다.

이 규칙을 정기적으로 자동 실행하는 검사로 만들려면 방법이 두 가지 있습니다.

  • 규칙 A의 범위를 넓힙니다. item이 달라도 비교하도록 바꾸면 이 쌍을 잡을 수 있습니다. 다만 그러면 "item과 무관하게 같은 주체·대상을 비교한다"는 규칙 B와 역할이 겹쳐서, 두 규칙이 각각 무엇을 담당하는지 구분하기 어려워집니다.
  • 이 쌍만 잡는 새 규칙을 추가합니다. 예를 들어 "주체(subject)와 대상(object)은 같고 relation은 다른 Claim을 item과 무관하게 찾는다"는 조건입니다. 규칙 수는 늘어나지만 규칙 A와 규칙 B의 역할은 그대로 유지됩니다.

두 방법 중 어느 쪽으로 할지는 아직 정하지 않았습니다.

# 규칙 B — 같은 subject·object·relation을 가진 서로 다른 claim_id (동일 주장 중복 서술 탐지, item 무관)
PREFIX prov: <https://ontology.gwanhak-inmul.kr/prov#> SELECT ?c1 ?c2 WHERE { ?c1 prov:hasSubject ?s ; prov:hasObject ?o ; prov:hasRelation ?r . ?c2 prov:hasSubject ?s ; prov:hasObject ?o ; prov:hasRelation ?r . FILTER(?c1 != ?c2) }
※ 위 두 쿼리는 실제로 실행해서 얻은 결과가 아닙니다. 아래 목록과 같은 사례를 찾으려면 어떤 조건을 걸어야 하는지 보여 주는 설명용 예시 쿼리입니다. 규칙 B는 belongsToItem을 조건에 넣지 않으므로, 아래 대성학교 사례처럼 서로 다른 item(item-2, item-21)에 속한 Claim끼리도 탐지할 수 있습니다. 같은 item 안에서만 비교하는 규칙 A와는 비교 범위가 다릅니다.
